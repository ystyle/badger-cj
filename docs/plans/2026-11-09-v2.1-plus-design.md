## 2. P0：正确性与资源收口（建议 2.0.1）

### P0-1 compaction 后废弃 .sst 文件回收

- **现状**：compaction.cj 的 deleteTables 只做 handler.removeTables + 表 close（解除映射），
  **全仓没有删除表文件的调用**；manifest 里已有 Delete 记录，但文件永久残留。
- **后果**：磁盘占用随 compaction 单调增长（被合并掉的旧表从不回收），长时间运行的
  服务（忆时塔/cjreg/tsdb）会持续膨胀；容器/备份场景尤其明显。
- **方案**：摘表 → close 映射 → unlink 文件（**Windows 必须先 close 再 unlink**，
  与 2.0 生命周期约定一致）；可选：open 时清理「manifest 里不存在」的孤儿 sst
  （崩溃窗口里已建表未提交 manifest）。删除动作放在锁外（close 可能慢）。
- **验收**：多轮 compaction 后，目录里 .sst 文件数 == manifest 活表数；
  崩溃/并发读用例（迭代器持有已删表）通过；Windows 路径由 CI 可见性覆盖。
- **工作量**：小（1-2 天，含测试）。
- **证据**：compaction.cj:409 deleteTables；progress-tracking 2026-10-06「既存缺口」条目。

### P0-2 flush 构建内存偏高（低堆下无法落盘）

- **现状**：64MB 堆下，两种表数据模式**都**先撞 flusher: flush system error
  （2026-10-06 记录）——瓶颈在 flush 自身构建工作内存，不在表数据是否驻留。
- **后果**：嵌入式/受限堆部署（chronomem 曾按 256MB 堆运行）对小堆不友好；
  与「2.0 让堆与数据量解耦」的目标不一致。
- **方案（二选一）**：① 单表大小上限 + 构建产物分段落盘（与 P1-1 流式 builder 合并）；
  ② 先做「flush 峰值内存」度量与预算，再决定分块粒度。
- **验收**：64MB 堆 + 大 memtableSize 能完成 flush；给出峰值内存与数据量关系曲线。
- **工作量**：中（与 P1-1 合并后摊薄）。

### P0-3 Windows 生命周期收口（close → unlink）

- **现状**：Windows CI 上 LargeBatchTest / ManagedDbTest 等 close 后立即 remove(dir)
  报 -32「文件被另一进程使用」；与 P0-1 是同一生命周期问题的两面。
- **方案**：统一「先 close 映射/句柄，再 unlink」；测试侧等待/独立临时目录只作兜底，
  不掩盖真实句柄泄漏。
- **验收**：Windows CI 该类 ERROR 清零（构建与其余用例保持绿）。
- **工作量**：小（与 P0-1 同批）。

## 3. P1：性能（有实测依据）

### P1-1 块缓存（Block Cache，覆盖非压缩场景）

- **依据（2.0 实测，A/B 交替 5 轮）**：mmap 随机读比「整表驻留堆」慢 2.7-3.2x
  （128MB：112.3 vs 35.5 µs/Get；16MB：20.8 vs 7.6）；v1.6.x 两模式都整表预读
  （35.2 vs 35.2，零差异）。原因：mmap 模式每块读 = memcpy + 新数组（GC 分配），
  而堆内模式的 Block 切片走 COW 共享。
- **方案**：可配容量的块 LRU（例如 64/128/256MB 或按比例），命中即复用块字节；
  与 TableData 解耦（缓存层在 Table 之上），关闭时行为与 2.0 完全一致。
- **验收**：相同场景（128MB/16MB）读延迟回到堆内模式的 1.1x 以内；
  内存上界可控（缓存容量 + 元数据）；全量测试绿。
- **工作量**：中（3-5 天，含淘汰策略与并发）。
- **备注**：原 2.0 计划认为「块缓存只对压缩/加密有意义」，实测推翻——非压缩也值。

### P1-2 L2 流式 TableBuilder（块完成即写文件）

- **现状**：builder 仍是 blocks: ArrayList<Array<Byte>> + finish() 一次拼接（L1 单拷贝）；
  L2（真流式、不驻留整表）在 async-flusher 文档中标注「另行排期」。
- **收益**：flush/compaction 峰值内存从「整表」降到「单块 + 缓冲」，
  与 P0-2 一体解决；压缩/加密路径的前置条件。
- **方案**：builder 增加 sink 回调/分段写；Table 数据源改为「已落盘文件 + 映射」，
  构建期不再返回整表字节；io_uring 分段写路径同步改造。
- **验收**：flush 峰值内存与表大小解耦（曲线）；产物与现有格式逐字节/结构等价
  （golden 指纹 + 全量测试）；io_uring 开/关均绿。
- **工作量**：中大（5-8 天）。

### P1-3 写路径收尾（建议只做评估）

- 2.0 vs 1.6.23 写吞吐 +6.9%（A/B 9 轮）；WAL mmap 比 buffered 快 8.5x；
  调研结论「组提交收益只来自减少唤醒次数」。**不建议**换队列/加无锁结构。
- 可选：msync 次数与 WAL 段切换策略的小评估（只做数据，不改默认语义）。

### P1-5 memtable Arena 公式对齐（比调优更实质，建议 2.0.1 或 2.1 最前）

- **现状（代码核对）**：memtable.cj:36 的 arenaSize = MemTableSize * 2，WAL 段容量直接取同一个
  arenaSize（memtable.cj:55）；而 go 的 arena 公式是 MemTableSize + maxBatchSize +
  maxBatchCount*MaxNodeSize（约等于 1x MemTableSize），go 的 WAL 段才是 2x MemTableSize。
- **后果**：每个 memtable 的堆占用约是 go 的 2 倍。默认 MemTableSize=64MB 时单个 arena 就是
  128MB；NumMemtables=5 的背压上限意味着峰值可到约 640MB —— 这与「低堆（64/128MB）跑不动」
  和 chronomem 的历史 OOM 直接相关，比 P1-4「调优」更值得先做。
- **方案**：arena 改 go 公式（含批次最坏预留），WAL 段容量与 arena **解耦**（WAL 仍按
  2x MemTableSize 预分配）；rotation 阈值从「arena 的 75%」改为对齐 go 的 shouldFlush
  （约 100% MemTableSize）；group commit 的每请求最坏预留逻辑保持。
- **验收**：默认配置下单个 memtable 堆占用约减半；小堆（64/128MB）+ 默认 MemTableSize 能写入并
  完成 flush；全量测试绿；写入 A/B 不回退。
- **工作量**：小-中（1-2 天 + 测试）。

### P1-6 Pebble 式 arena 渐进扩容（在 P1-5 之上叠加）

- **做法**（见图示）：第 1 个 memtable 的 arena = min(256KB, 目标 arena)，之后每新建一个 memtable
  翻倍，达到目标值后不再增长。只在「创建 memtable 时」决定大小——skiplist 的插入/查找/遍历
  逻辑一行不用改（arena 一旦分配不能搬家，指针都指向内部）。
- **收益**：冷启动/低写入量场景下，空闲 memtable 的 arena 从 128MB 降到 KB 级；缓解与 flush
  builder 峰值的叠加；对「打开即吃几百 MB」的嵌入式部署最直接。
- **注意**：与 P1-5 一起做；arena 与 WAL 段容量解耦后不会互相牵制（WAL 稀疏预分配，段内写偏移
  自然小，不浪费物理页）。
- **验收**：空库/小负载的 RSS 与堆曲线下降；单测断言前 N 个 memtable 的 arena 尺寸序列
  （256KB→512KB→...→cap）；连续写入吞吐 A/B 不回归。
- **工作量**：小（<1 天 + 测试）。

## 4. P2：可运维性与工程清理

### P2-1 Stats / Metrics API（当前完全缺失）

- **现状**：全仓无 getStats/Stats 类，生产只能看日志。
- **建议内容**：Get/Scan 计数与命中率（memtable/imm/L0/L1+）、flush/compaction 次数与
  耗时、VLog GC 统计（可丢字节/重写段数）、活跃迭代器数、各层表数/字节数、
  WAL 段数/写偏移。
- **实现**：轻量快照结构（不可变 Stats 类）+ 原子计数；不引 Prometheus 依赖
  （由宿主转换）。**验收**：单元测试覆盖字段口径；chronomem/cjreg 接入示例。
- **工作量**：中（2-3 天）。**ROI 高于块缓存**，建议与 P0 一起进 2.0.1/2.1。

### P2-2 Encryption（2.1 候选）

- 先出算法决策文档（R3），再实现：段头/块级 IV、KEYREGISTRY、FORMAT features gate。
- 验收：开启后读写正确、关闭可读旧库、性能损耗有基线；**不做**与 go 的密文互通。

### P2-3 CloseableBlockingQueue 简化

- 官方 LinkedBlockingQueue 自带阻塞 remove()，可去掉手写 Condition 循环；
  注意多消费者 close 需哨兵唤醒。工作量：小。

### P2-4 user key 互为前缀的限制写入 README

- 已定性（docs/issue/2026-11-09-read-miss-after-compaction.md）：keyWithTs 原始字节比较下，
  user key 互为前缀（ck-1 / ck-10）会导致 seek 歧义、部分 get 落空；等宽 key 实测 0 缺失。
- 在 README 兼容性/使用注意加一条：**user key 不应互为前缀**（与 Go badger 一致），
  并指向 issue 文档。工作量：极小（纯文档）。
