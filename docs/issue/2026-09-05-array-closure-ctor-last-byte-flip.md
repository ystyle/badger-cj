# 编译器 bug：特定形状下 Array(n, {j=>}) 闭包构造末元素按位取反

> 2026-09-05 · badger-cj 排查 crc 疑点时发现 · cjc 1.1.3（cjpm 1.1.3）· Linux x86_64
> 状态：已最小复现，待上报编译器团队

## 现象

**静态函数内** `Array<Byte>(L, {j => f(j)})` 闭包构造的大数组（L ≥ ~30000，L 为**运行时传入的参数**），
数组**最后一个元素 = 期望值按位取反**（`got = 0xFF ^ want`），其余元素全部正确。

最小复现（badger-cj `src/table` 测试环境，-O2 与 -O0 均复现）：

```cangjie
private static func content(L: Int64): Array<Byte> {
    Array<Byte>(L, {j => UInt8((j * 7 + 3) % 256)})
}

// 触发：L 来自数组迭代的运行时值，且 L >= 约 30000
let lengths = [30000, 30001, ...]
for (L in lengths) {
    let arr = content(L)
    // arr[arr.size-1] == 0xFF ^ UInt8(((L-1)*7+3)%256)   ← 错（应为不取反）
    // arr[0..arr.size-2] 全部正确
}
```

实测（L=30000，期望尾字节 76=0x4C）：`got=179=0xB3 = 0x4C ^ 0xFF`。
逐字节 diff 仅 1 处（尾字节）；经 `ArrayList` 逐字节 add → `toArray()` 的对照数组**全部正确**。

## 触发条件（已确认）

| 条件 | 结果 |
|------|------|
| `content(L)` 静态函数内构造，L 为函数参数（运行时值） | **翻转** |
| L ≥ 约 30000（16384 以下未触发；30000/30357/65536 全触发） | **翻转** |
| 同函数、同 L，在另一调用上下文（如 `for (L in [20000,30000,...])` 形状不同的循环） | **不翻转** |
| 调用点内联构造 `Array<Byte>(L, {j=>...})`（L 为局部变量） | **不翻转** |
| `ArrayList` 逐字节 add 后 `toArray()` | 正确 |
| -O2 vs -O0 | 均翻转（排除优化 pass） |
| crc 相关：输入内容与 CRC 完全无关；换 crc 依赖为本地源码编译 | 翻转依旧 |

## 排查排除项

- **crc-cj 库 / 溢出策略**：`update` 全为 XOR/移位（无溢出运算，`@OverflowWrapping` 无作用对象）；
  且换本地源码编译、-O0 均复现 → 与 crc 模块、制品边界、溢出注解无关
- 内容生成与 CRC 无关：数组内容是 `(j*7+3)%256` 纯算术

## 结论

语言/编译器（cjc）对「函数内参数化长度的闭包构造数组」存在**确定性错误代码生成**
（末元素取反，疑似闭包迭代上界/写回逻辑错误），依赖调用点代码形状触发。

## 影响面（badger-cj）

- 生产代码仅 `block_iterator.cj:159` 一处 `{j=>}` 构造（key 重建，长度 = key 长 ≤ 65000，
  形状与触发条件（函数参数+大 L）不完全一致，-j1 全绿未见异常），风险待观察；
- 测试代码大量 `{j=>}` 构造数据，但 -j1 全绿说明形状未触发；
- **workaround 建议**：数据构造统一走「`Array(n, repeat: 0)` + 循环赋值」或
  ArrayList → toArray，规避闭包构造路径。

## 最小化上报素材

待整理为单文件（main + content + for 循环 + 尾字节断言）提交编译器团队；
复现依赖「函数调用 + 数组迭代传参 + 大 L」组合，建议编译器侧从闭包构造的
长度下界/闭包调用边界代码生成入手。
